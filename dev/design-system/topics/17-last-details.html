Topic 17: five details the spec left open

Writing design-system.md turned up five small things none of the decisions covered. Each is drawn below with a proposal. Hover the icons in Q1; press "Run" in Q5.

Q1Tooltip: how soon, and which side

A. 400ms, above

Shows after a short rest on the icon, above it.

SearchDownload

B. 800ms, above

Only when you wait; passing the pointer over a row of tools shows nothing.

SearchDownload

C. 400ms, below

Below the icon, where it covers the content under the header row.

SearchDownload
Proposal: A, 400ms, above. Long enough that moving across the header row shows nothing, short enough that a pause gets the name. Above, because the tools sit at the top of a block and a tooltip below would cover the title or the first field. It flips below only where there is no room above (top of the viewport). Runner-up: B.

Q2A count on a secondary or destructive button

A. The host's colour

The count takes its button's text colour: accent on main, default on secondary, red on destructive.

B. Always accent

Every count is the accent tint, whatever its button.

C. Always neutral

Every count is grey; colour stays with the button.

Proposal: A, the host's colour. It is the B3 rule ("tint of the host") carried to the other two buttons, so a count never brings a second colour into a button. Runner-up: C.

Q3The block status dot when inputs are not set yet

The dock header shows a dot for a block that cannot run yet because a required input is empty. Today it is #eab308, a yellow outside the palette.

A. Amber (warning)

amber-500, the palette's warning edge colour: "needs something from you".

IN
Read data
read block
Set this block's inputs

B. Grey

text-disabled: "not running", with no alarm.

IN
Read data
read block
Set this block's inputs

C. Hollow ring

An empty circle in muted: "not filled in yet".

IN
Read data
read block
Set this block's inputs
Proposal: A, amber. It matches the required-empty cue on the input itself (a soft amber edge and fill), so the dot and the field it points to say the same thing, and it comes from the palette. Runner-up: C.

Q4An error or warning that belongs to the whole block

A block whose expression fails, or that dropped rows, shows it inside the block. Section 8 already has a message style (status text, fill and edge); nothing says blocks use it.

A. The message style

Tinted fill, edge and text, above the output.

Error. Column "Ozone2" not found in the data.

B. A bar on the left

Default text next to a red bar; no fill.

Error. Column "Ozone2" not found in the data.

C. In the status line

A red line in the block's status line at the foot.

● Column "Ozone2" not found in the data.
Proposal: A, the message style, above the output. One style for every message in blockr, and an error has to be seen before the output it explains; a warning uses the amber set, the same shape. Runner-up: C, for warnings only (dropped rows), where a line at the foot is enough.

Q5A block that is computing

The composer dims the old table and shows a clock ("composing… 1.2 s") when a compose takes longer than 300ms. Other blocks show nothing while they compute.

A. Composer only (today)

Other blocks show nothing until they update.

B. Every block, the composer's cue

Past 300ms any block dims its output and shows the clock under it.

C. Every block, a line at the top

Past 300ms a thin accent line runs along the block's top edge; nothing dims.

Proposal: B, the composer's cue for every block. A slow block (a model, a large join) today looks frozen; the cue already exists and was tuned (nothing under 300ms, time shown), so blockr.core can apply it to any block from outside. Runner-up: C, if dimming the output is too much.
