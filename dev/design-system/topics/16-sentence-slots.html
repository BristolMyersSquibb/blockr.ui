Topic 16: the sentence and its slots, when a block has many settings

The sentence with live words stays: an underlined word opens its own list, an unset setting shows as a dashed "+" offer. It is the one way a setting reaches the face of a chart or table block (pinned-controls.md). Your issue on the CDEx tables: with many inputs the sentence runs on, values and offers blur into one paragraph, and every input has to be written into the sentence by hand before it shows. Four questions, drawn on the AE grade table. On a BMS board the accent, and so the slots, are purple.

Q1Many settings: one sentence, or one line each?

A chart's sentence names two or three settings and reads as prose ("Mean ozone by Month, coloured by Year"). The table blocks name a setting per clause with a label in front ("Rows:", "Grades:"), which is a list. An author can already break a line: \n in the title, subtitle or caption template is a line break (blockr.viz tt_line_breaks(), commit 947d05c).

A. One sentence (today)

All clauses run on. Where one value ends and the next label starts depends on the wrap.

Proposal: B, one line per setting whenever the sentence is a list of labelled clauses, which is every table and code block; charts with a real sentence keep A. The author writes \n between clauses, which works today. The clause's label ends the line, so no full stops. Runner-up: C, for a block with more than four settings on its face.

Proposal: B, first three and a count. The cut moves from 8 to 3. Runner-up: A, if exports must list every value.

Q4Who writes the sentence

Today a setting reaches the face only if the script's author names it in the #| subtitle: template; every new input means editing the template, and an input left out stays in the gear. The spec already says a block with no template gets one generated, one "label: value" per input, but the composer does not do this yet.

A. Always authored (today)

Full control of the wording; nothing shows until someone writes it.

rows   <- c("AESOC", "AEDECOD")  # column
grades <- c("Any Grade (%)", ...)
pool   <- NULL

#| subtitle: Rows: {@rows}.\nGrades: {@grades}.[\nPooled as: {@pool}.]

B. Generated unless authored

No template: one line per input, the input's label and its value, offers for the unset ones. A template, if written, wins. (The | Rows label syntax is a sketch.)

rows   <- c("AESOC", "AEDECOD")  # column | Rows
grades <- c("Any Grade (%)", ...)  # | Grades
pool   <- NULL                    # | Pooled as

# no #| subtitle: line needed

C. Always generated

One rule for every code block; the author sets labels and order, never prose.

rows   <- c("AESOC", "AEDECOD")  # column | Rows
grades <- c("Any Grade (%)", ...)  # | Grades
pool   <- NULL                    # | Pooled as
Proposal: B, generated unless authored. A new input shows up on the face the moment it is declared, as a line of its own (Q1) or an offer (Q3), and an author who wants prose still writes it. It is what the spec already describes, so the work is in the composer block, not in the design. Runner-up: C, if consistency across code blocks matters more than prose.

Recorded as they are

  • The slot mark: accent text, dashed underline, solid on hover; the click opens the list under the word (Blockr.Select.menu).
  • An offer is a dashed chip in muted text, accent on hover, gone once its setting is set.
  • A clause in [ ... ] leaves with its value; the sentence never prints "(none)".
  • One template, two renderers: the face draws live words, exports print the same text.
